stdexec under C++29, in Tony Tables

What representative parts of stdexec, and one user's function, could look like in a C++29 with D4471's async functions, D4481's operation_handle, and result destinations decided as 4A. Each section says what its table shows, then shows it.

Status

  • The C++29 column is a strawman. D4481 isn't drafted under 4A, so the protocol's names are placeholders chosen here: destination<Sig>(), complete<Sig>(), slot<T>, values<A, B>, continuation, completion_table. The direct-style syntax is D4471R0's (branch d4471r0, commit def2626), plus one spelling D4471 lists as open.
  • The C++26 column isn't stdexec's source. stdexec builds its algorithms from __sexpr machinery that would make a column unreadable, so the algorithms are hand-written to the C++26 protocol, following what stdexec does where it matters (its let_value, for instance, also destroys the first child when it starts the second). Section 1's left column is P4223R2's cache.cpp as published, and section 10's is P4223R2's erased receiver.
  • Simplifications shared by both columns: a child with one value signature (value_of<S> stands for computing it from completion signatures), when_all of two children that doesn't forward its parent's stop token, sync_wait returning optional<V> rather than optional<tuple<V>>, and no attributes or domains.
  • What was compiled (observed). Every table's code is cut verbatim from source files that were compiled and run with GCC 13.3 and Clang 18.1 (the GCC builds under ASan and UBSan): the C++26 column against stdexec main 30acdb0; the C++29 column against a library stand-in for the protocol; the C in section 12 as C11 with -pedantic. The exceptions are section 1's right column, which needs the language feature, and the two P4223R2 excerpts. The tests check values, errors, stopped paths where they exist, an immovable result, and move counts.
  • Not shown: the async stack beyond a bump pointer, arguments in place, tail calls, environments behind erasure, attributes, domains, and the protocol negotiation between C++26 and C++29 senders.

The C++29 vocabulary

start and every completion return an operation_handle: the next thing to run, or nothing (D4481). A receiver answers two member templates keyed by a completion signature. destination<Sig>() says where to construct that completion's payload, and complete<Sig>() says the payload has been constructed there. A receiver may also provide a set_value member that takes a value where the sender keeps it, as in C++26; execution::set_value(rcvr, v) calls it if it exists, and otherwise constructs v at the destination and completes. Section 4 explains why that third member is there. All of this is source form, which is what WG21 would standardize.

When a receiver is erased, its member templates are instantiated once per declared completion into a static table, and the caller's record is one pointer to that table (4A). That's the ABI, which a platform fixes. Section 10 shows it, and sections 11 and 12 show what code compiled against it looks like.

slot<T> is storage for a T that someone else constructs, and it remembers whether it holds one. The design needs a type like it because std::optional can't hand out the address of storage it hasn't constructed into. stdexec has __manual_lifetime, which is the same idea without the flag.

Corrections to the sample

  • The sample's then was movable, in both columns. Nesting it inside let_value made libstdc++'s variant::emplace build it in a temporary and move it, leaving its child pointing at the temporary (ASan: stack-use-after-return). Every operation state below now deletes its move constructor, as stdexec's do.
  • The sample said when_all is a case only 4A expresses. It isn't. Its children's values can go straight into the parent's storage under any of 3A, 4A and 5A, because the parent's destination is known when when_all starts. The one place a destination decided at completion looked useful (letting the first failing child claim the parent's error storage) turned out to be unsafe; section 7 says why.

1. The user's code: cache::get

P4223R2's caching decorator over a kv_store, as published, beside the same function written as a D4471 body. The declaration is the same in both. Nothing about destinations, tables or handles shows on the right: that choice is between the compiler and the ABI, and someone writing direct-style code never sees it. Section 11 shows what the compiler would make of the right column.

lookup cache::get(std::string key) const noexcept {

    if (auto value = entries_.find(key)) {
      co_return value;
    }
    auto value = co_await backing_->get(key);
    if (value) {
      try {
        entries_.insert(key, *value);
      } catch (...) {
        // caching is best-effort; the lookup succeeds
      }
    }
    co_return value;
  } catch (std::error_code ec) {  // the backing store's error: pass it on

Two things on the right are still open in D4471. with_error is P4282R2's spelling, one of the candidates D4471 lists for completing with a chosen error. And the catch (std::error_code) handler is needed because, under D4471's rule, catch (...) would otherwise be entered by the backing store's set_error(error_code), and what current_exception() returns there is undecided.

2. A leaf that completes inline: just

The smallest sender. The only change is that start returns what the receiver says runs next. execution::set_value(rcvr, std::move(value)) now does one of two things. If the receiver can use the value where just keeps it, it is passed by reference, as in C++26. Otherwise it is constructed at the receiver's destination. Section 4 is about that choice.

3. A middle that filters one completion and passes the rest: then

This is Robert Leahy's case in its most common form. then consumes its child's value, because it needs it to call f, and passes errors and stopped through untouched. On the left the split is spread across three completion members. On the right, each of the two member templates has one if constexpr. For the value, then answers with storage of its own. For everything else it answers with its parent's answer, so a child's error is constructed directly wherever the top of the chain keeps it. The set_value member takes the value where the child keeps it, when the child offers that. Either way, f's result is constructed in the parent's storage.

The C++26 column handles any number of value signatures through its variadic set_value. The C++29 column needs storage per value signature, which would be a slot per signature, or a union of them.

C++26
template <class Child, class F, class R>
struct then_op {
  using operation_state_concept = operation_state_t;

  struct rcvr_t {
    using receiver_concept = receiver_t;
    then_op* op;

    template <class... Vs>
    void set_value(Vs&&... vs) && noexcept {

C++29
template <class Child, class F, class R>
struct then_op {
  using operation_state_concept = operation_state_t;
  using V = value_of<Child>;
  using U = std::invoke_result_t<F, V>;

  struct rcvr_t {
    using receiver_concept = receiver_t;
    then_op* op;

    // the child's value, where the child keeps it
    operation_handle set_value(V&& v) noexcept {
      return op->invoke(std::move(v), false);
    }

    template <class Sig>
    void* destination() noexcept {
      if constexpr (same_as<Sig, set_value_t(V)>) {
        return op->value.address();  // filtered: then needs it
      } else {
        return op->rcvr.template destination<Sig>();  // passed through
      }
    }

    template <class Sig>
    operation_handle complete() noexcept {
      if constexpr (same_as<Sig, set_value_t(V)>) {
        return op->invoke(std::move(op->value.adopt()), true);
      } else {
        return op->rcvr.template complete<Sig>();
      }
    }

    env_of_t<R> get_env() const noexcept {
      return execution::get_env(op->rcvr);
    }
  };

  F f;
  R rcvr;
  slot<V> value;  // the child constructs its value here
  connect_result_t<Child, rcvr_t> child;

  then_op(Child&& c, F fn, R r)
      : f(std::move(fn)), rcvr(std::move(r)),
        child(execution::connect(std::move(c), rcvr_t{this})) {}
  then_op(then_op&&) = delete;

  operation_handle start() & noexcept { return execution::start(child); }

  operation_handle invoke(V&& v, bool ours) noexcept {
    bool ok = true;
    try {
      ::new (rcvr.template destination<set_value_t(U)>())
          U(std::invoke(std::move(f), std::move(v)));
    } catch (...) {
      ::new (rcvr.template destination<set_error_t(exception_ptr)>())
          exception_ptr(std::current_exception());
      ok = false;
    }
    if (ours) {
      value.reset();  // before completing: the parent may destroy *this
    }
    return ok ? rcvr.template complete<set_value_t(U)>()
              : rcvr.template complete<set_error_t(exception_ptr)>();
  }
};
  • An immovable result now works (observed). With f returning a type whose move constructor is deleted, the C++26 column fails to compile in stdexec's sync_wait (a static assertion, then no matching emplace), because the value arrives as an argument and has to be stored. The C++29 column constructs it in the root's storage.
  • Nothing of then's is touched after it completes its parent. That rule is C++26's too. What's new is that destroying the child's value is then's job, and it has to happen before complete, which is why invoke resets the slot first.

4. Your question: may just call set_value instead?

Yes, and it should. In the sample, just(x) | then(f) cost one more move than in C++26, because just constructed its value in then's storage, where C++26 handed f a reference into just's operation state. Letting the sender choose set_value gets that move back. The table compares the two C++29 forms of just; the set_value member that receives the reference is then's, in section 3.

So the rule that falls out is simple. A sender whose value already exists and outlives the call offers it by reference with set_value. A sender that creates its value constructs it at the destination. The set_value form never cost more moves than C++26 here, and creating values is where the design saves.

Why the choice belongs to the sender, and what it costs, ranked:

  1. Only the sender knows whether the value already exists. The receiver knows only whether it needs storage. With execution::set_value defaulting to construct-and-complete, a receiver that has no use for a reference writes nothing extra, so offering a reference never costs a receiver anything.
  2. A receiver that takes the reference must finish with it before completing its own parent. That's C++26's rule, since the child is still alive underneath the call. It holds for then. It also means a receiver can't destroy the child while it holds the reference, which only matters to an algorithm that wants to release children as they complete.
  3. Pass-through layers should forward set_value, as write_env and let_value's second receiver do below. One that doesn't still works: the default constructs at its destination, which is its parent's. It only loses the reference.
  4. Across erasure the reference is lost unless the ABI carries it. Section 10's erased receiver has no set_value, so a just behind a function constructs into the caller's destination. A table could gain one by-reference entry per value signature, at the cost of a bigger table and an ABI with two ways to deliver a value. I'd leave it out until a measurement shows it matters, since behind an erased call the caller usually needs storage anyway.

This supersedes the idea the sample raised, a leaf declaring set_value_t(T&&), which would have changed the declared completions to get the same effect.

5. A middle that passes everything through: write_env

The common case. Every completion goes to the parent unchanged, and only the environment differs. On the left that means three forwarding members; on the right, three forwarding members of a different kind. Neither column needs any storage, and on the right every payload is constructed directly in whatever storage the nearest ancestor that filters provides. The environment line is the same in both columns.

6. Storage that outlives a child: let_value

let_value keeps its first child's value for as long as the second child runs, because f receives it by reference and the second sender may borrow it. Both columns destroy the first child when they start the second, as stdexec does: variant::emplace does it, while the first child is still inside its completion call, which is safe only because the child touches nothing afterwards.

Two things differ. On the left the first child's value arrives as an argument and is moved into an optional. On the right the child constructs it in let_value's slot, or, if the child chose set_value, the default does the same. And everything the second child produces passes straight through to the parent's storage, where the left column hands each value up as an argument for someone further up to store. With just on both sides the two columns make the same number of moves; with a second child that creates its value, the right makes one fewer (section 4).

C++26
template <class Child, class F, class R>

    using receiver_concept = receiver_t;
    let_value_op* op;

    template <class A>

      op->next(std::forward<A>(a));
    }

    template <class E>
    void set_error(E&& e) && noexcept {
      execution::set_error(std::move(op->rcvr), std::forward<E>(e));
    }

    void set_stopped() && noexcept {
      execution::set_stopped(std::move(op->rcvr));
    }

    env_of_t<R> get_env() const noexcept {
      return execution::get_env(op->rcvr);
    }
  };

  struct rcvr2_t {  // the second child's: everything passes through
    using receiver_concept = receiver_t;
    let_value_op* op;

    template <class... Vs>
    void set_value(Vs&&... vs) && noexcept {
      execution::set_value(std::move(op->rcvr), std::forward<Vs>(vs)...);
    }

    template <class E>

      execution::set_stopped(std::move(op->rcvr));

  R rcvr;

7. Several children at once: when_all

The fork. On the left each child's value arrives as an argument, is moved into an optional in when_all, and is handed on by reference when when_all completes, for its parent to move again if it stores it. On the right, when_all asks its parent once, at start, where the pair of values goes. It then gives each child the address of its own element, so every value is constructed in its final place. A child whose value is created fresh (a then, say) costs no moves at all, against one per child on the left (section 4's last row), and a parent that stores the pair would move each value once more on the left only.

Errors are different, and this is the one place the right column stages a payload and moves it. Both children can fail at the same time, so each gets an error slot of its own, and the winner is moved to the parent at the end. The right column also loses the left's try/catch: a value whose construction throws is the child's failure, reported as the child's error, not when_all's.

This table needs four protocol rules that the simpler algorithms never touched. Each is a question for D4481:

  1. A sender may ask for a destination before it knows how it will complete, and abandon it. when_all asks for the value destination at start, and on error or stopped it destroys what its children constructed there and completes some other way. The rule needed: a sender may hold several destinations but have live objects in only one at a time, and must destroy them before constructing in another. Without that, a parent couldn't put its value and error storage in one union, and every parent does.
  2. The value aggregate has to be constructible one element at a time. values<A, B> stands in for D4471's unnamed aggregate, and the stand-in builds its elements in anonymous unions to make that legal. No C++ class with non-trivial members allows it. If the aggregate is compiler-defined, the language could grant it; if it is a library tuple, it can't.
  3. Why a destination decided at completion doesn't help here. The tempting design lets the first failing child claim the parent's error storage, which only 4A can express. It's unsafe: the error storage may share a union with the value elements another child is constructing at that moment.
  4. Starting two children means running what the first hands back. start returns one handle, so the first child's has to be run in place (execution::run) before the second starts. The nesting is bounded: the first child's chain ends in when_all's arrive, which returns nothing because the second child hasn't finished.

The C++29 column keys the value destination as set_value_t(Vs), the aggregate. A real signature would be set_value_t(V1, V2), with the aggregate as what its destination holds; the stand-in uses one key for both to stay short.

8. A leaf that completes later: run_loop

A scheduler's operation states queue themselves in start, and the loop completes them later. On the right, start returns an empty handle, meaning nothing is ready yet. The task function returns whatever its receiver's completion hands back, and the loop runs that before taking the next task. That makes the loop the bottom of the machine stack, which in D4481 is the job of whoever drives the work. set_value_t() has no payload, so this leaf never asks for a destination. The queue itself (a mutex, a condition variable and a list) is the same in both columns and is left out.

9. The root: sync_wait

Where the asynchronous world ends. On the left, the receiver stores what arrives and tells the loop to finish. On the right it answers with addresses in its own state, notes which completion happened, and returns an empty handle, because nothing above it is waiting. The loop is also given whatever start returned, since an operation that completes inline hands its continuation back rather than running it.

C++26
template <class V>
struct sync_wait_state {
  run_loop loop;
  std::optional<V> value;
  exception_ptr error;
};

template <class V>
struct sync_wait_receiver {
  using receiver_concept = receiver_t;
  sync_wait_state<V>* st;

  template <class A>
  void set_value(A&& a) && noexcept {
    try {

The last line moves the value out of the slot into the returned optional, because optional has no way to let someone else construct into it. That one move is where the destination chain meets synchronous code, and it's a reason for D4481 to propose a slot-like type, or a way to construct into an optional, rather than leave every algorithm to write one.

10. The erased boundary: where 4A lives

Sections 2 to 9 are what WG21 would standardize. This is what a platform's ABI would fix: what a receiver turns into when the callee can't see its type, as behind P4223's function. The left column is P4223R2's own erased receiver, with its completions. The right is the same receiver under 4A, in two halves: the callee's side, which the implementation is connected to, and the caller's side, where a composed receiver's member templates become a static table, as vtable_for does on the left.

The erased receiver shrinks from a target, a vtable and an environment to one pointer to the caller's record, whose only member is a pointer to a static table. The table has one destination function per completion that carries a payload, in place of one completion function per signature. And complete returns a handle instead of calling through the table, so an inline completion unwinds to the caller, which can carry on in place, rather than nesting a call.

The frame holds only what lives across the one suspension. Its table answers "where?" with the frame's own variables: the local value and the handler's ec share a union, because the child constructs one or the other. That's the member template of section 3, instantiated twice and erased. The answers are static here. A frame that passed a completion through would answer with its caller's destination instead, which is where 4A's chaining or resolving-once would show.

The entry and the resume function
async_next cache::get_entry(std::string* key, async_cont* k,
                            async_sp sp) const noexcept {
  try {
    // if (auto value = entries_.find(key)) co_return value;
    // Nothing has suspended yet: this runs on the machine stack, no frame.

      return async_complete(k, VALUE);

    return fail(k, std::current_exception());  // catch (...)

  void* mem = async_push(&sp, sizeof(cache_get_frame));
  cache_get_frame* f;
  try {
    f = ::new (mem) cache_get_frame({&cache_get_table}, k, this, key);
  } catch (...) {  // copying the key into the argument threw
    return fail(k, std::current_exception());

  // auto value = co_await backing_->get(key);
  async_next n = backing_->get_entry(&*f->arg, f, sp);

  }
  return n;  // pending: whoever completes it runs us later

async_next cache_get_resume(async_cont* c, int how) noexcept {
  auto* f = static_cast<cache_get_frame*>(c);
  async_cont* k = f->k;
  f->arg.reset();  // the full-expression ends: the argument goes
  async_next done;
  switch (how) {
    case VALUE:
      f->has_value = true;
      // if (value) { try { entries_.insert(key, *value); } catch (...) {} }
      if (f->value) {
        try {
          f->self->entries_.insert(*f->key, *f->value);
        } catch (...) {
        }
      }
      // co_return value;
      ::new (async_destination_of(k, VALUE)(k))
          std::optional<std::string>(std::move(f->value));
      done = async_complete(k, VALUE);
      break;
    case ERROR:  // catch (std::error_code ec) { co_return with_error(ec); }
      ::new (async_destination_of(k, ERROR)(k)) std::error_code(f->ec);
      done = async_complete(k, ERROR);
      break;
    default:  // stopped: no handler sees it
      done = async_complete(k, STOPPED);
  }
  f->~cache_get_frame();  // and the frame is popped: our caller's top never moved
  return done;
}
  • The hit path has no frame. Nothing has suspended before co_return value, so that path runs on the machine stack like a synchronous function and constructs the result straight into the caller's destination. kv-handle measured the same thing (0 B of frame storage on a hit). It does mean the frame is allocated at the first suspension point that can actually suspend, not at entry, which bears on the open question of whether frame allocation belongs to connect or start: an allocation failure becomes reportable only on the paths that allocate.
  • Each completion is the caller's to run. Every path ends by returning {k, how}. If the child completed inline, its returned handle names this frame's record, and the entry carries on in place (the fall-through) instead of returning to a loop.
  • The argument dies at the end of its full-expression, before the rest of the body runs, as D4471 specifies for temporaries.
  • A missed optimization worth naming. The catch (std::error_code ec) handler only passes ec on. A compiler could see that and give the child its caller's error destination directly (a pass-through), removing the copy. For error_code that's nothing; for an error type that can't be copied, it decides whether the body compiles.
  • co_return value on the miss path moves, as return value; does in a synchronous function with two returned variables. Constructing the local in the caller's storage, in the manner of NRVO, would save it, but no compiler does that for the synchronous equivalent either.

12. The same kind of leaf, in C

A backing store written in C, behind the same ABI, completing later from an event loop, or inline with an error for an empty key. Its interface uses C types (c_value, an int error), so either side of it could be written in C. It was compiled as C11 with -pedantic and called from a C++ root (observed). The C code does what a C++29 leaf does: it asks where the payload goes, constructs it there, and returns the caller's record instead of calling it.

c_store.h
/* The C++ declaration this entry stands behind:
 *
 *   using c_lookup = function<
 *       sender_tag(c_store const*, char const*) noexcept,
 *       completion_signatures<set_value_t(c_value), set_error_t(int),
 *                             set_stopped_t()>>;
 *   c_lookup c_store_get(c_store const* store, char const* key) noexcept;
 */
typedef struct c_value {
  char const* data; /* NULL when the key is absent */
  size_t len;
} c_value;

enum { C_VALUE = 0, C_ERROR = 1, C_STOPPED = 2 };

async_next c_store_get_entry(c_store const* store, char const* key,

c_store.c
/* What lives across the suspension: our frame on the async stack. */
typedef struct get_frame {
  task task; /* first, so the loop can run it */
  c_store const* store;
  char const* key;
  async_cont* k; /* our caller's record */
} get_frame;

/* Runs from the event loop, after the entry returned "pending". */
static async_next get_later(task* t) {
  get_frame* f = (get_frame*)t;
  async_cont* k = f->k;
  char const* found = find(f->store, f->key);

  c_value* v = async_destination_of(k, C_VALUE)(k); /* ask: where? */
  v->data = found;
  v->len = found ? strlen(found) : 0;
  /* the frame is popped: our caller's top never moved */
  return async_complete(k, C_VALUE); /* returned, not called */
}

async_next c_store_get_entry(c_store const* s, char const* key,
                             async_cont* k, async_sp sp) {
  if (key[0] == '\0') { /* an empty key is an error, reported inline */
    int* e = async_destination_of(k, C_ERROR)(k);
    *e = EINVAL;
    return async_complete(k, C_ERROR);
  }
  get_frame* f = async_push(&sp, sizeof *f);
  f->task.run = get_later;
  f->store = s;
  f->key = key;
  f->k = k;
  defer(&f->task);
  async_next pending = {NULL, ASYNC_PENDING};
  return pending;
}

What C can't express is the static part: the destination member templates, the completion signatures and the if constexpr choices. A C implementation sees only the erased form, so its declared completions live in a comment and in the order of the table's functions. That's the README's argument 4 (4A's table is a plain struct of function pointers) seen from the C side. Stopped isn't wired up: the environment, and so the stop token, isn't in the ABI yet.
